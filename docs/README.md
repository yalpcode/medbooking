## 1. Пояснительная записка

### 1.1. Описание предметной области

Система MedBooking предназначена для поликлиники или медицинского центра, где пациенты записываются на прием к врачам определенных специальностей. Система хранит сведения о пациентах, врачах, специальностях, рабочих периодах врачей, временной недоступности врачей и фактических приемах.

Основные пользователи:

- регистратор: создает карточки пациентов, ищет свободные слоты, записывает и отменяет приемы;
- врач: видит свое расписание на день и историю приемов;
- администратор клиники: управляет врачами, специальностями, рабочими периодами и анализирует загрузку;
- пациент: выбирает специальность, врача, дату и свободное время приема.

Ключевые сценарии:

1. Пациент выбирает специальность и дату, система показывает свободные слоты.
2. Регистратор записывает пациента на конкретное время.
3. Два пользователя не могут записать разных пациентов к одному врачу на один и тот же интервал.
4. Пациент не может быть записан на два активных приема, пересекающихся по времени.
5. При болезни врача клиника массово отменяет затронутые приемы и фиксирует период недоступности.
6. Администратор анализирует загрузку врачей и популярность специальностей.

### 1.2. Функциональные требования

Система должна поддерживать:

- ведение справочника медицинских специальностей;
- регистрацию пациентов с уникальными телефоном и номером полиса ОМС;
- ведение врачей, лицензий, кабинетов и набора специальностей врача;
- создание рабочих периодов врача с шагом слота;
- фиксацию периодов недоступности врача;
- поиск свободных слотов по врачу, специальности и дате;
- создание, перенос, подтверждение, завершение и отмену приема;
- просмотр расписания врача на день;
- просмотр истории приемов пациента;
- аналитические отчеты по загрузке врачей, специальностям и неявкам.

Операции над данными:

- `CREATE`: создать пациента, врача, специальность, рабочий период, запись на прием;
- `READ`: найти свободные слоты, расписание врача, историю пациента, агрегированную загрузку;
- `UPDATE`: изменить контактные данные, перенести прием, отменить прием, завершить прием;
- `DELETE`: удалить только справочные или тестовые записи без зависимых приемов; для приемов используется отмена, а не физическое удаление.

### 1.3. Нефункциональные требования

- **Согласованность.** Запись на прием должна быть защищена на уровне БД, а не только на уровне приложения.
- **Многопользовательский доступ.** Одновременные регистраторы могут искать слоты и пытаться записать пациентов; конфликт должен завершаться ошибкой ограничения, а не двойной записью.
- **Производительность.** Поиск по врачу, пациенту, дате и активным приемам поддерживается индексами.
- **Аудит.** Изменения статуса приема логируются в отдельной таблице `appointment_status_history`.
- **Сопровождаемость.** Предметные ограничения вынесены в `CHECK`, `FOREIGN KEY`, исключающие ограничения и триггеры.

### 1.4. Предварительная схема БД

На раннем этапе можно было бы хранить записи в одной таблице:

```text
raw_appointments(
  patient_name, patient_phone, oms_policy_number,
  doctor_name, doctor_license, doctor_specialties,
  work_date, work_start, work_end, room,
  appointment_start, appointment_end, appointment_status
)
```

Эта схема удобна для первого списка требований, но содержит повторения и аномалии. Поэтому итоговая модель разделена на сущности: `patients`, `doctors`, `specialties`, `doctor_specialties`, `doctor_work_periods`, `doctor_time_off`, `appointments`, `appointment_status_history`.

Визуальная ER-диаграмма находится в `diagrams/er_diagram.svg` и включена в PDF-отчет.

### 1.5. Текстовые ограничения на данные

- Каждый пациент имеет уникальный номер полиса ОМС.
- Каждый пациент имеет уникальный телефон.
- Каждый врач имеет уникальный номер лицензии.
- Врач может иметь одну или несколько специальностей.
- Специальность может относиться к нулю или более врачам.
- Прием всегда относится ровно к одному пациенту, одному врачу и одной специальности.
- Прием у врача возможен только по специальности, которая назначена этому врачу.
- Начало приема должно быть раньше конца приема.
- Длительность приема ограничена интервалом от 10 минут до 2 часов.
- Активные приемы одного врача не могут пересекаться по времени.
- Активные приемы одного пациента не могут пересекаться по времени.
- Рабочие периоды одного врача не могут пересекаться.
- Прием нельзя создать вне рабочего периода врача.
- Прием нельзя создать в период недоступности врача.
- Активный прием не имеет даты отмены, а отмененный прием обязан иметь дату отмены.
- Статус приема меняется только в рамках допустимого жизненного цикла: `booked`, `confirmed`, `completed`, `cancelled_by_patient`, `cancelled_by_clinic`, `no_show`.

### 1.6. Формализация ограничений

Функциональные зависимости:

- `patient_id -> last_name, first_name, middle_name, birth_date, sex, phone, email, oms_policy_number`
- `phone -> patient_id`
- `oms_policy_number -> patient_id`
- `doctor_id -> last_name, first_name, middle_name, license_number, phone, email, room, hire_date, is_active`
- `license_number -> doctor_id`
- `specialty_id -> code, name, description`
- `code -> specialty_id`
- `(doctor_id, specialty_id) -> experience_years, is_primary`
- `work_period_id -> doctor_id, work_date, starts_at, ends_at, slot_minutes, room`
- `appointment_id -> patient_id, doctor_id, specialty_id, starts_at, ends_at, status, reason`

Многозначные зависимости:

- `doctor_id ->> specialty_id`: у врача может быть несколько независимых специальностей.
- `doctor_id ->> work_period_id`: у врача может быть множество рабочих периодов.
- `patient_id ->> appointment_id`: у пациента может быть множество приемов.
- `appointment_id ->> status_history_id`: у приема может быть множество записей истории статусов.

Дополнительные зависимости предметной области:

- `(doctor_id, tsrange(starts_at, ends_at))` для активных приемов должен быть уникален по пересечению интервалов.
- `(patient_id, tsrange(starts_at, ends_at))` для активных приемов должен быть уникален по пересечению интервалов.
- `(doctor_id, specialty_id)` в `appointments` должен существовать в `doctor_specialties`.

### 1.7. Нормализация

**1НФ.** Устраняем повторяющиеся группы: список специальностей врача не хранится строкой `doctor_specialties`, а выносится в отдельную таблицу `doctor_specialties`. Все атрибуты становятся атомарными.

**2НФ.** Устраняем частичные зависимости в связующих таблицах. В таблице `doctor_specialties` атрибуты `experience_years` и `is_primary` зависят от полного ключа `(doctor_id, specialty_id)`, а не только от врача или специальности.

**3НФ.** Устраняем транзитивные зависимости. Название специальности не хранится в записи приема; прием содержит `specialty_id`, а название находится в `specialties`. ФИО и телефон пациента не дублируются в `appointments`.

**BCNF.** Основные детерминанты являются ключами или кандидатными ключами: `phone`, `oms_policy_number`, `license_number`, `code`. Связь врача и специальности выделена отдельно, поэтому данные о специальности не зависят от врача транзитивно.

Итоговая схема снижает дублирование и переносит критичные ограничения в БД.

### 1.8. Анализ недонормализованной схемы

Проблемная сырая таблица:

```text
raw_appointments(
  appointment_id,
  patient_name,
  patient_phone,
  oms_policy_number,
  doctor_name,
  doctor_license,
  specialty_name,
  room,
  appointment_start,
  appointment_end
)
```

Аномалия обновления: если врач переезжает из кабинета `304` в `307`, нужно обновлять кабинет во всех строках будущих приемов. Одна пропущенная строка приведет к противоречивым данным.

Аномалия вставки: нельзя заранее добавить нового врача без приемов, потому что таблица описывает только факты приемов.

Аномалия удаления: если удалить последний прием пациента, можно потерять сведения о пациенте, хотя он должен остаться в базе.

Нормализованная схема решает проблему: врач, пациент и специальность живут независимо от приема; прием хранит только ссылки.

### 1.9. SQL DDL

Итоговый DDL находится в `sql/01_schema.sql`. Важные решения:

- `EXCLUDE USING gist` запрещает пересечение активных приемов у одного врача.
- Второе исключающее ограничение запрещает пациенту иметь два активных приема в одно время.
- Составной внешний ключ `(doctor_id, specialty_id)` не дает записать пациента к врачу по чужой специальности.
- Триггер `trg_validate_appointment_schedule` запрещает прием вне рабочего периода и во время недоступности врача.
- Триггер `trg_appointments_audit_status` ведет историю статусов.

### 1.11. Транзакции

Критичные операции находятся в `sql/04_transactions.sql`.

**Запись на прием.** В одну транзакцию входят проверка врача, проверка доступности слота и вставка приема. Даже если два регистратора одновременно выберут один слот, ограничение `appointments_no_doctor_overlap` пропустит только одну вставку.

**Перенос приема.** Транзакция блокирует строку приема `FOR UPDATE`, затем меняет время. Без этого можно получить потерянное обновление: один сотрудник переносит прием, другой одновременно отменяет или переносит его в другое время.

**Болезнь врача.** В одной транзакции отменяются все будущие активные приемы в интервале отсутствия врача и добавляется период `doctor_time_off`. Если сделать только часть операции, система либо покажет врача доступным, либо сохранит активные приемы в период болезни.

**Завершение приема.** Статус меняется атомарно, а триггер автоматически пишет историю.

### 1.12. Пользовательский интерфейс

Интерфейс не реализуется, потому что в рамках работы оценивается проектирование БД и SQL. Возможный минимальный UI: форма поиска слотов, карточка пациента, дневное расписание врача, панель администратора.

## 2. Приложение по использованию AI

> Важно: этот раздел подготовлен как репрезентативная версия для итогового документа. Перед сдачей его стоит заменить фактическими фрагментами вашей переписки с AI и результатом реальной проверки второй моделью, если преподаватель требует именно журнал взаимодействия.

### 2.1. Репрезентативные фрагменты работы с основной AI-моделью

**Фрагмент 1. Извлечение требований**

- Запрос: «Помоги выделить сущности и ограничения для системы записи к врачу: пациенты, врачи, специальности, расписание, приемы».
- Ответ модели: «Нужны сущности `patients`, `doctors`, `specialties`, связь врач-специальность, расписание врача, приемы. Критичные ограничения: запрет двойной записи к одному врачу, проверка рабочего времени, статусы приемов».
- Уточнение команды: «Не просто перечисли сущности, а покажи, какие ограничения должны быть реализованы именно в БД».
- Комментарий: полезным было выделение пересечений интервалов как ограничения БД; поверхностным было первоначальное отсутствие проверки специальности врача.

**Фрагмент 2. Выбор способа защиты от двойной записи**

- Запрос: «Как надежно запретить запись двух пациентов к одному врачу на одно время в PostgreSQL?»
- Ответ модели: «Можно использовать уникальный индекс по `(doctor_id, starts_at)`, но он не защищает от пересекающихся интервалов разной длительности. Лучше использовать exclusion constraint по `tsrange(starts_at, ends_at)`».
- Уточнение команды: «Добавь также запрет пересекающихся активных приемов у одного пациента».
- Комментарий: решение с `EXCLUDE USING gist` оказалось сильнее простого уникального индекса, потому что учитывает интервалы.

**Фрагмент 3. Нормализация**

- Запрос: «Покажи, почему нельзя хранить пациента, врача, специальность и прием в одной таблице».
- Ответ модели: «Возникнут аномалии обновления, вставки и удаления: изменение кабинета врача надо повторять в каждой строке, нельзя добавить врача без приема, удаление последнего приема удалит сведения о пациенте».
- Уточнение команды: «Свяжи эти аномалии с переходом к 1НФ, 2НФ, 3НФ и BCNF».
- Комментарий: полезной была структура объяснения; команда уточнила зависимости, чтобы раздел нормализации был не декларативным.

**Фрагмент 4. Проверка DML**

- Запрос: «Проверь, покрывают ли запросы основные операции CRUD и есть ли сложные запросы».
- Ответ модели: «CRUD покрыт: создание пациента, поиск слотов, изменение контактов, отмена приема, удаление тестовой записи. Сложные запросы используют `JOIN`, `GROUP BY`, агрегаты, оконные функции».
- Уточнение команды: «Добавь пояснение, кто пользователь каждого запроса и почему он важен».
- Комментарий: после уточнения запросы стали лучше соответствовать формату задания.

### 2.2. Независимая верификация второй моделью

Каркас запроса для второй модели:

```text
Ты — старший архитектор баз данных с большим практическим опытом и критическим стилем рецензирования. Я даю тебе описание предметной области, логическую модель данных, DDL-скрипт и набор SQL-запросов. Найди не менее 3 потенциальных проблем, спорных решений или слабых мест. Обрати внимание на аномалии, зависимости, нормализацию, ограничения целостности, производительность и альтернативы моделирования.
```

Репрезентативные замечания рецензента:

1. Простого уникального индекса по `(doctor_id, starts_at)` недостаточно, если длительность приемов может отличаться. Решение: использовать exclusion constraint по временному диапазону.
2. Если прием хранит `specialty_id`, нужно доказать, что врач действительно имеет эту специальность. Решение: добавить составной FK `(doctor_id, specialty_id)` на `doctor_specialties`.
3. Проверка свободного времени только в приложении опасна при конкуренции. Решение: вынести проверку пересечения и рабочего периода на уровень БД.
4. Периоды недоступности врача могут конфликтовать с активными приемами. Решение: добавить триггер, запрещающий создать `doctor_time_off` поверх активных приемов, пока они не отменены.
5. Для отчетов по расписанию нужны индексы по врачу, пациенту и времени приема. Решение: добавить индексы `appointments_doctor_starts_idx`, `appointments_patient_starts_idx`, частичный индекс активных приемов.

### 2.3. Комментарий команды по AI

Полезные замечания:

- заменить уникальный индекс на exclusion constraint;
- добавить запрет пересечения приемов не только для врача, но и для пациента;
- добавить составной внешний ключ для проверки специальности врача;
- учитывать периоды недоступности врача отдельно от обычного расписания.

Спорные или отклоненные предложения:

- предложение генерировать и хранить каждый слот отдельной строкой было отклонено: в текущей модели слоты вычисляются из рабочих периодов через `generate_series`, что уменьшает объем данных;
- предложение хранить ФИО врача в `appointments` отклонено как денормализация, создающая аномалии обновления.

Изменения после проверки:

- добавлены исключающие ограничения для врача и пациента;
- добавлен триггер проверки рабочего периода;
- добавлено представление `v_doctor_work_slots`;
- добавлен аудит изменения статусов приема.

## Быстрый запуск SQL

PostgreSQL запускается через Docker Compose:

```bash
docker compose up -d
```
